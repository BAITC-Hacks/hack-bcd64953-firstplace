# Архитектура

Frontend -> Supabase Auth (пароли/сессии). Frontend -> FastAPI `/api/v1` (Bearer JWT)
-> зависимости авторизации/роли -> сервисы -> репозитории -> Supabase SDK/PostgreSQL.
Сервисы отдельно обращаются к Storage и AI-провайдеру через httpx.

JWT проверяется PyJWT: подпись ES256/RS256, exp/iss/aud/sub, audience=authenticated,
sub=UUID, claim role=authenticated. Прикладная роль берётся только из profiles.
JWKS кэшируется 5 минут, неизвестный kid инициирует обновление с cooldown SDK.
Ошибки: неверный токен 401, роль 403, чужой объект 404, недоступный JWKS 503.

SDK-клиент создаётся на запрос и закрывается после него; пользовательские Auth-сессии не
устанавливаются на service role клиенте. Синхронные SDK/httpx/pandas выполняются в worker pool.
Все прикладные таблицы имеют RLS. Браузеру разрешено прочитать только собственный profiles;
остальные таблицы и RPC доступны лишь service_role. Поэтому сервисы и транзакции обязательно
проверяют владельца. CSV видит автор загрузки, бизнес — после отклика на свою заявку.

## Состояния

- Заявка: draft -> published -> closed; редактируется только draft.
- revision увеличивается при изменении. PostgreSQL блокирует строку и сравнивает версию.
  ИИ-анализ, ответы и CSV-оценка привязаны к версии; устаревшее состояние даёт 409.
- Вопросы/ответы и заявка обновляются одной транзакцией.
- Отклик: pending -> accepted/rejected. Один отклик на пару заявка/команда.
  Повторная отправка — 409, повтор одинакового решения идемпотентен, смена решения — 409.
- submit_response повторно проверяет опубликованность, владельца CSV, актуальную оценку
  и порог не ниже 90; создаёт отклик и уведомление атомарно.
- decide_response атомарно сохраняет решение и уведомление студента.
- Несколько команд могут быть приняты на одну заявку.

## Формулы

| Поле готовности | Баллы |
|---|---:|
| title | 5 |
| description | 10 |
| goal | 15 |
| target_audience | 10 |
| expected_result | 15 |
| timeline | 10 |
| available_data | 10 |
| success_criteria | 15 |
| required_skills | 10 |

Публикация при 100%; Python и триггер БД считают одинаковую заполненность.
Заполненность не доказывает содержательное качество описания.

Matching = floor(85 * доля покрытых навыков + 15 * min(1, максимальный опыт / требуемый опыт)).
Если требуемый опыт равен нулю, компонент опыта равен 15. Навыки сравниваются по trim/casefold,
без семантических синонимов. Используется объединение навыков и максимальный опыт участника.
MATCH_THRESHOLD можно повышать от 90 до 100. ИИ не задаёт проценты и не принимает решений
о доступе/публикации/откликах. Его ответ проходит строгую Pydantic-валидацию.

Документация: [Supabase JWT/JWKS](https://supabase.com/docs/guides/auth/jwts),
[Python 3.14.7](https://www.python.org/downloads/release/python-3147/).
